## 8. Real-pipeline bug: CPS-transformed method called from a constructor

Found by the stakeholder trying `withDotnet`/`dotnetWrapper` in a real Jenkins pipeline (`junes_journey/tools/cli` PR-400): every invocation with no explicit selector failed with `Found unhandled hudson.remoting.ProxyException exception: CpsCallableInvocation{methodName=validateSelectors, ..., arguments=[null, null, null]}`. Root cause: `Dotnet`'s constructor calls `validateSelectors(...)`, a method on the same class. Jenkins CPS-transforms every method on classes under `src/` by default, but constructors themselves cannot be CPS-transformed (they can't be paused/resumed) — calling a CPS-transformed method from a constructor leaks an unhandled `CpsCallableInvocation` continuation object instead of executing it. This class of bug is invisible to the Spock/`jenkins-pipeline-unit` test harness, which doesn't perform real CPS transformation, so it wasn't caught until real Jenkins execution.

- [x] 8.1 Annotate `Dotnet.validateSelectors(...)` with `@NonCPS` (`import com.cloudbees.groovy.cps.NonCPS`), matching the repo's existing convention (`BuildVersion.groovy`) for methods that must run as plain, non-resumable Groovy.
- [x] 8.2 Re-run the full Gradle test suite to confirm the annotation doesn't change behavior for the existing (CPS-blind) test harness — 409/410 pass, same pre-existing unrelated `CacheSpec` failure.
- [x] 8.3 Document the risk in `design.md` (Decision 1) so future model classes in this library avoid calling same-class methods from constructors without `@NonCPS`, or avoid the pattern entirely.

## 11. Real Windows bug: PowerShell array splat is positional, not named

Found by the stakeholder on a real Windows agent (first real Windows run of `withDotnet`, a `global.json`-derived `channel: "10.0"` build): `dotnet-install.ps1` failed with `'10.0' is not a supported value for -Quality option`, even though the wrapper never sets `-Quality` anywhere. Root cause: `$selectorArgs = @('-Channel', $selector.Value)` spliced via `@selectorArgs` is an **array** splat, which PowerShell binds **positionally** — each element becomes a separate positional argument, not a `-flag value` pair. Since the official script's `param()` block declares `$Channel` first and `$Quality` second, the literal string `"-Channel"` bound positionally to `$Channel`, and `"10.0"` bound positionally to `$Quality` — never actually reaching `-Channel` as a named parameter at all. Reproduced exactly (byte-for-byte matching error) with a stub script replicating the real param block, before touching the fix.

This was invisible to every test run so far: the Groovy/Spock suite never executes `dotnet-install.ps1`'s actual logic (only that `jenkins.powershell(...)` was called with *some* script), and earlier manual `pwsh` validation on macOS tested `Resolve-Selector` in isolation (no invocation) and the real official script with hand-typed named args (`-Channel 8.0`, never through the `$selectorArgs` splat variable) — so the splat bug's actual invocation path was never exercised end-to-end until a real Windows agent hit it.

- [x] 11.1 Fixed `$selectorArgs` in `dotnet-install.ps1` from an array (`@('-Channel', $value)`) to a hashtable (`@{ Channel = $value }`) — only hashtable splats (`@hashtable`) map keys to named PowerShell parameters; array splats (`@array`) are purely positional.
- [x] 11.2 Verified the fix with a stub script reproducing the real script's exact `param()` order: confirmed the buggy version reproduces the exact reported error, and the hashtable version correctly binds `-Channel`/`-Version` by name for both selector kinds.
- [x] 11.3 Re-ran the full wrapper end-to-end via `pwsh` on macOS with `DOTNET_CHANNEL=10.0` (the exact failing scenario): confirmed the `-Quality` error is gone and execution now proceeds to the same pre-existing, already-documented macOS/`pwsh`-only architecture-detection limitation (irrelevant on real Windows agents where `$env:PROCESSOR_ARCHITECTURE` is set).

## 12. Real Windows bug: Write-Host output not captured by 2>&1

Second bug found on the same real Windows agent, one fix later: after 11's parameter-binding fix, the dry-run resolved the version correctly and printed it to the console ("Repeatable invocation: ... -Version \"10.0.301\" ..."), but `dotnet-install.ps1` still failed with "Could not resolve an exact SDK version from dry-run output" — the regex found nothing in the *captured* `$dryRunOutput`, despite that exact text being visible in the Jenkins console. - [x] 12.2 Switched from `[regex]::Match` (first match) to `[regex]::Matches` + taking the last match, mirroring the bash wrapper's `tail -n1` behavior, for consistency and to reduce risk from any earlier version-like substrings in the output.

## 15. Reduce "Checks if running on a Unix-like node" step noise by memoizing isUnix()

Reported by a consumer: the Jenkins UI showed a large number of "Checks if running on a Unix-like node" step entries for a single `withDotnet`/`withDotnetTool` call. Root cause: `Dotnet.groovy` called `jenkins.isUnix()` (a real Jenkins step, not a plain check) at 8 separate call sites, and since `cacheDir()`/`toolCacheDir()` are themselves invoked from several other methods, a single `withDotnetTool { }` call chain could trigger 10+ separate `isUnix()` step invocations - each adding its own step entry to the build log/flow graph, since an agent's OS can't change mid-build and a single check per instance is sufficient.

## 17. Real production bug: dotnet tool install couldn't find a private NuGet package via withDotnetTool/runDotnetTool

Reported by a consumer (junes_journey/aviary_eggs pipeline, real Jenkins build): `runDotnetTool(packageId: "Wooga.Adv5.Tools", ...)` failed with `wooga.adv5.tools is not found in NuGet feeds https://api.nuget.org/v3/index.json.` — the private `wooga_nuget` feed was never even searched, despite the preceding `ensureNuGetSource()` step succeeding and registering it. "Works fine on my machine" because manual testing had only exercised `withDotnet`/`dotnetWrapper` (SDK-only path), never `withDotnetTool`/`runDotnetTool`'s tool-install path specifically.

- [x] 17.1 Root-caused via the real Jenkins build's step log (`get_node_steps`/`get_node_log` on the failing pipeline): `ensureNuGetSource()` (registering `wooga_nuget`) runs *before* `withTool()`'s `jenkins.withEnv(toolEnv())`, which sets `DOTNET_CLI_HOME` to the tool cache dir. Confirmed by real execution (not assumed) that `DOTNET_CLI_HOME` independently governs where `dotnet nuget`/`dotnet tool` read/write the user-level `NuGet.Config` (`$DOTNET_CLI_HOME/.nuget/NuGet/NuGet.Config`), completely separate from the real `$HOME` — a source registered under one `DOTNET_CLI_HOME` value is genuinely invisible under a different one. So `dotnet tool install` always ran against an empty, freshly-redirected `NuGet.Config` that never had `wooga_nuget` registered, deterministically for every tool-step call with a NuGet source configured.
- [x] 17.2 Fixed by re-calling `ensureNuGetSource()` a second time inside `withTool()`'s `toolEnv()`-scoped `withEnv` block, immediately before `installTool()`, when a NuGet source is configured. `ensureNuGetSource()` is already idempotent (checks before adding), so the extra call is cheap and safe. Credentials needed no equivalent fix - `NuGetPackageSourceCredentials_<source>` is read directly from the process environment by NuGet, not from `NuGet.Config`, so it was never scope-dependent.
- [x] 17.3 Real-execution verified both the bug and the fix directly against the `dotnet` CLI (not just Spock-against-fakes): registered a source under one `DOTNET_CLI_HOME`, confirmed it's invisible under a different `DOTNET_CLI_HOME` (reproducing the exact reported failure), then confirmed re-registering under that second `DOTNET_CLI_HOME` makes it visible there too (confirming the fix).
- [x] 17.4 Added tests (`DotnetSpec.groovy`): `withTool` re-registers the NuGet source when one is configured (asserting exactly 2 `nuget add source` calls - once at the SDK level, once inside `toolEnv()`), and skips re-registration entirely when no NuGet source is configured. Full suite: 461/461 pass.
- [x] 17.5 Updated `design.md` (Decision 11 revision) and `specs/dotnet-tool-steps/spec.md` (new requirement) to document that the configured NuGet source must remain visible under the redirected `DOTNET_CLI_HOME`.
- [x] 17.6 The 17.2 fix landed (confirmed the exact commit was checked out on the real agent), but the consumer's next real run (junes_journey/aviary_eggs #15) still showed only one `ensureNuGetSource()` invocation before the failing `dotnet tool install` - no visible evidence the second, `toolEnv()`-scoped call in `withTool()` actually ran, despite `nugetSourceName` being provably non-null on that same `Dotnet` instance (proven by the first call having run). Re-confirmed via fresh real execution that `DOTNET_CLI_HOME` alone (HOME unchanged) does redirect `NuGet.Config` resolution, and that a properly-visible `wooga_nuget` source does let `dotnet tool install Wooga.Adv5.Tools` succeed - so the underlying mechanism and fix are sound; the mismatch between "code is correct" and "real run doesn't show it executing" points at something in how the library is loaded/cached on that specific Jenkins instance (dynamically-loaded libraries can behave oddly if the same library name is loaded at differing versions more than once in a single build - Jenkins resolves to whichever version loaded first and silently ignores later differing requests) rather than a logic bug in this repo. Added a permanent diagnostic: `ensureNuGetSource()` now echoes/`Write-Host`s which `DOTNET_CLI_HOME` scope it's registering the source under, embedded in the existing `sh`/`powershell` call (no new step, so no test harness changes needed beyond `.contains()` assertions still matching). This makes the next real run unambiguous about whether the second call executes at all, without speculating further. Full suite: 461/461 pass.
- [x] 17.7 Root cause of the confusing repeated failures on builds #15/#16 identified: those were triggered via Jenkins **Replay**, which is documented/known to reuse the compiled pipeline/library state from the build being replayed rather than actually recompiling against the freshly-checked-out library revision - the checkout log looked fresh ("Checking out Revision ...") but the executed code was stale. A genuinely fresh trigger (`Build Now`) on the same unchanged consumer `Jenkinsfile`/content repo (no production content modified) confirmed the fix works correctly: build #20 succeeded across all four platform stages, `dotnet tool install Wooga.Adv5.Tools` resolving correctly against `wooga_nuget`.
